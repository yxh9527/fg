# 水池合并配置开发与验收说明

更新日期：2026-10-28

本说明对应《水池合并配置功能实施方案》，记录代码实现、运行方式和验证边界。代码尚未部署到线上，也未连接真实 MySQL、Redis、Elasticsearch 及游戏服做完整联调。

本文记录原单代理版本。默认方案、代理专属配置和新增代理自动同步已另行实现，需求见[改造方案](水池合并默认方案与代理自动同步改造方案.md)，新增实现及验证范围见[开发说明](水池合并默认方案与自动同步开发说明.md)。

## 一、已实现功能

- 控制管理新增“水池合并配置”页签，按当前代理管理分组。
- 支持新增、编辑、删除，允许每组 1–10 个游戏；同一代理下不能重复入组。
- 新组复制按加入顺序选中的第一个游戏的有效配置，优先代理配置，再取默认配置。
- 新组累计数据从零开始，余额从复制配置的 Base 开始，不转入原游戏余额。
- 编辑名称、顺序或成员保留原组配置与余额；移出游戏重新独立累计。
- 删除组后，所有成员分别从自己的初始配置重新累计，不分摊组余额。
- 入组时定向清理原独立池运行数据，保留原配置、历史注单、钱包流水和审计记录。
- 清理覆盖内存缓存、Redis 运行记录及定时写回保护，避免旧快照重新生成原池。
- 重置沿用既有周期和排期，改为持久化任务执行；组定义和配置在重置后保留。
- 游戏设置中的旧配置列表展示组归属，禁止通过已入组游戏误改失效的独立配置。

## 三、管理接口

接口前缀：`/api/auth/v2/govern/pool-groups`。沿用管理后台 M 账号权限，token 按现有方式放在查询参数中。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | /api/auth/v2/govern/pool-groups | 当前代理的组、余额和最近操作记录 |
| GET | /api/auth/v2/govern/pool-groups/detail | 查询组详情 |
| GET | /api/auth/v2/govern/pool-groups/games | 查询可选游戏，过滤其他组成员 |
| GET | /api/auth/v2/govern/pool-groups/operation | 查询操作状态 |
| POST | /api/auth/v2/govern/pool-groups/create | 新增 |
| POST | /api/auth/v2/govern/pool-groups/update | 编辑 |
| POST | /api/auth/v2/govern/pool-groups/delete | 删除 |

查询需带 agentId；详情和操作查询另带 id；游戏列表编辑时带 groupId。可选 webId 用于校验代理所属站点。

新增和编辑使用 JSON 请求体，字段包括 agentId、groupId、version、requestId、name、symbols。新增的 groupId 和 version 为 0；编辑和删除须提供当前组 ID 和版本。删除无需 name 和 symbols。

requestId 是同一代理下的请求唯一编号：同内容重试复用同一编号，内容变化使用新编号。响应成功表示任务提交成功，只有操作状态 applied 表示整个配置任务确认完成。

## 四、持久化和执行机制

新增表：pool_group、pool_group_member、pool_group_operation。现有 web-api 初始化会注册迁移；lottery 执行器启动也显式检查迁移错误。

pool_group_member 对代理 ID 和游戏标识建立联合唯一约束。同一代理的管理操作串行处理，编辑还校验版本，避免覆盖他人修改。

组运行统计复用现有四类代理水池统计集合，但使用内部组标识 `@pool_group:<组ID>` 作为水池身份。注单和报表继续保留真实游戏标识。

运行配置、切换门禁、活动链和处理中请求使用 app/poolgroup.Key 统一生成带项目前缀的 Redis key。定时重置在持久化任务后广播带批次编号的 resetPool 事件，ResetPool 收到后同步尝试执行该批次，不再只写 MySQL；后台 MySQL 轮询用于未完成任务和通知丢失时的重试。

每个代理的资金请求与切换任务共享 Redis 租约。资金请求读取当前运行配置，刷新内存快照，并在租约保护下持久化；Lua 写入会校验持有者，避免丢锁后的旧实例覆盖余额。

切换状态：pending（待执行）、waiting（等待结算）、applying（切换中）、applied（已确认）、failed（失败待重试）。

切换流程：登记受影响游戏门禁 → 允许旧链继续结算并等待收敛 → 原子写入新归属、清理指定旧池并记录操作编号 → 刷新内存、解除门禁 → SQL 事务确认分组关系及完成状态。SQL 确认失败时重试，不再清理已开始累计的新池。

重置触发时间和周期继续沿用原设置；实际生效须等待该代理未结算链收敛，可能晚于触发时刻。后台执行记录显示等待原因。

## 五、订单与异常处理边界

- Slots 免费预占按预占、实际使用和退款登记活动余额。
- Fruit、UG5 连续链按协议中的 complete 标记结束。
- 多人投注按玩家、游戏和币种累计未结束投注，退款和结算后扣减。
- Luck5 在发牌时固定原池身份、版本和 Base，结算使用原池；启动时恢复已持久化的未结束局。
- 资金请求先登记处理中标记；发生结果未知的异常时保留现场，阻止切换任务清除相关池。
- 已确认资金持久化、只缺会话确认的成功请求支持同请求恢复；无法确定结果的资金异常不能通过盲目重放或直接删 key 处理，需先对照原请求、钱包和流水核实。
- Luck5 另有持久化资金阶段，同一发牌或结算请求可依靠原阶段结果恢复，避免重复扣款或派奖。
- 当前没有自动猜测金额或一键清理未知资金操作的管理入口。
- 若运行配置缺失而数据库已有生效分组，服务明确报错并等待恢复，不默认为空组或零余额。

## 六、部署与首次启用

1. 在测试环境备份并验证现有 MySQL 配置、Redis 水池运行数据和未结束游戏链。
2. 首次升级先停止新下注，完成升级前已开始的免费链、竞猜链、多人局和其他长局。升级前这些链并未统一登记在新活动账中，不能仅依据新账为空判断可清池。
3. 完成所有 lottery 实例及 web-api 的升级，确认新表迁移成功，再恢复流量、开放水池分组管理。旧开奖实例不理解新分组和租约，不能与新版本混跑。
4. 验证真实游戏端的 complete、预占退回、多人退款与结算字段均符合现有协议，再启用生产分组。
5. 按新增、追加成员、移出成员、删除组和周期重置逐项验收，并检查重启后的归属及余额。

当前 Lua 原子操作沿用项目既有全局统计 key，适用于单 Redis 或 Sentinel 拓扑。Redis Cluster 需要先调整同槽 key 设计并完成联调，不能直接套用当前多 key Lua。

启用分组后，回退旧二进制也必须先维护、完成未结束链并验证独立池恢复，不能直接让旧代码读取已清除的原独立池。

## 八、ResetPool 重置链路回归修复

- 定时器恢复发布 resetPool 事件，周期参数和每分钟的到期检查不变。
- ResetPool 先持久化、再同步执行可处理的任务，不能仅以数据库任务入库认定重置成功。
- 重置在代理租约内扫描并清除四类 Redis 水池累计统计，覆盖已删除游戏和已删除代理残留数据。
- Redis 清理成功后，零化缓存对象及待写回标记，再清空该代理的水池缓存映射；原组定义和初始配置保留。
- 每个通知接收实例均按运行版本同步本机内存，即使另一实例已完成该批次，也不会保留旧池缓存。
- 相同批次重复触发不会再次清理新投注；丢锁或 Redis 执行失败时不伪造内存已清空。
- 存在未结算订单或前序任务时，状态保持等待并记录原因，不能记录为已完成；其他可处理代理继续执行。

专项测试使用 miniredis 验证 Redis 真实命令与内存对象：清理后旧统计消失、余额回到 Base、旧快照不能复活数据、重复批次保留新投注、失败保留原缓存、已执行批次同步其他实例的旧内存。数据库提交与任务查询在批次入口测试中使用测试替身；真实 MySQL 联调仍未执行。

## 十、选择代理后新增按钮不可用的修复

- 原先新增按钮同时受代理选择和任何未完成操作记录限制；重置任务等待或失败时，按钮会直接置灰且缺少就近说明。现在选择有效代理后可以打开新增弹窗，未完成任务仅限制最终提交，并显示操作编号、类型、状态和执行说明。
- 原先弹窗要等待可选游戏接口成功才显示；网络慢或接口失败时，点击表现为无反馈。现在先显示弹窗，再展示加载状态；失败会显示具体原因，支持重新获取游戏并保留草稿。
- 分组列表接口增加 pendingOperation，查询该代理最早的未完成操作，避免阻塞任务超出最近 30 条历史后页面无法解释原因。
- 切换代理、关闭弹窗或重新请求时，旧可选游戏响应不会覆盖当前弹窗。
- 保留后台任务串行和版本校验，不自动删除、跳过或伪造完成资金任务。

## 十一、测试代理 ID 0 的兼容

- ID 0 是现有开奖协议认可的系统虚拟测试代理，不要求代理表存在对应记录；管理接口也按相同约定处理，不为它创建虚假代理行。
- null、undefined、空字符串表示未选择；数值 0 和字符串 0 都表示明确选择测试代理，不能再用真值判断或大于零条件混淆两者。
- 路由参数和缓存中的代理 0 在刷新后保持为测试代理，不回退到默认配置或历史正式代理。缓存选项 ID 统一为数字；没有测试选项时补充系统测试代理选项。
- POST 必须显式提供 agentId，缺失或 null 不会自动落到测试代理 0。负数和无效文本继续拒绝。
- 正式代理仍校验代理表记录及查询时的站点归属；测试代理不校验不存在的代理表站点归属。测试池仍按代理 ID 隔离，因此 ID 0 在不同站点展示的是同一个系统测试代理。
- 测试代理配置提交使用现有代理 0 Redis 租约串行保护；正式代理保持原数据库行锁逻辑。权限、成员唯一性、版本和未完成任务校验继续有效。
- 新增测试覆盖代理 0 的读取、配置提交参数、路由/缓存恢复、空选择区分、无代理表读取、JSON 字段存在性、共享租约竞争，以及 Redis 分组创建/编辑/删除和正式代理隔离。真实 MySQL 新增事务仍需部署环境验收。
