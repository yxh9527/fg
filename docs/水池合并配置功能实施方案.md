# 水池合并配置功能实施方案

更新日期：2026-10-28

文档状态：已实现代码及自动化测试，待真实环境联调与上线验收。实现入口、验证范围和部署要求见[开发与验收说明](水池合并配置开发与验收.md)。

## 一、需求与方案范围

管理后台支持新增、编辑、删除游戏共用水池。同一代理、同一水池组内的游戏共用水池，不同代理之间保持隔离。

### 已确认的业务规则

1. 新建或周期重置后，从初始配置重新累计，不汇总历史数据重算。
2. 编辑组成员时保留组余额。
3. 游戏使用新水池后，清除原游戏独立水池的运行数据。
4. 游戏移出水池组后，重新开始独立水池计算。
5. 新增时，游戏选择列表自动过滤已经加入水池组的游戏。
6. 新组默认采用第一个加入游戏的水池配置。
7. 每组最多选择 10 个游戏。
8. 水池重置周期沿用原有设置。

### 本方案采用的设计约定

- 分组按后台当前选中的代理维护，同一代理下，一个游戏最多加入一个组；其他代理的配置和余额互不影响。
- 允许保留只有一个游戏的组，避免移除成员后自动解散。空组不允许保存，清空成员应通过删除组完成。
- 首版将成员编辑与组参数修改分开处理，避免修改 Base 时隐式改变余额。

上述设计约定属于本方案建议，需在实施时与业务规则一并核对。

## 二、各操作的业务规则

| 操作 | 组水池如何处理 | 游戏独立水池如何处理 |
| --- | --- | --- |
| 新建水池组 | 复制第一个选中游戏的有效水池配置，从该配置的初始值开始累计 | 成员切换成功后，清除原独立池运行数据 |
| 给现有组增加游戏 | 保留现有组余额，新游戏后续投注、赔付计入组池 | 清除新加入游戏的独立池运行数据，不将旧余额转入组池 |
| 从组里移除游戏 | 保留组余额，不拆分、不退还该游戏过去贡献的金额 | 从该游戏自己的初始配置重新累计 |
| 同时增加、移除游戏 | 原组继续使用，保留余额和累计数据 | 新加入的清理旧池，移出的新建独立池 |
| 修改组名称、成员顺序 | 保留余额和组配置 | 无额外变更 |
| 删除整个组 | 停止使用并清除组池运行数据 | 原成员分别从各自初始配置重新累计 |
| 到达原有重置周期 | 组池累计数据清零，从组配置的初始值重新累计 | 未入组游戏继续沿用原有重置规则 |

“重新累计”不等于余额归零。现有代码的水池余额口径为：

`水池余额 = 初始值 Base + 累计有效投注 − 累计赔付 − 累计税收`

因此，新建或重置后的累计数据为零，起始余额为配置中的 Base。赔付预占、退款、汇率及金额精度继续遵循现有计算规则。

## 三、后台页面设计

在“控制管理 → 游戏设置”区域新增“水池合并配置”页签，沿用当前站点、代理筛选条件。

### 列表内容

- 组名称。
- 成员游戏。
- 游戏数量。
- 当前组余额。
- 配置来源游戏。
- 运行状态。
- 更新时间。
- 编辑、删除操作。

### 新增弹窗

- **组名称**：必填。
- **成员游戏**：支持搜索、多选，展示已选数量，最多 10 个。
- **初始配置来源**：明确显示第一个加入的游戏。
- **水池参数预览**：展示复制的 Base、水位、税收及控制参数。
- **操作说明**：明确提示“创建后重新累计，原独立水池运行数据将清除”。

### 游戏选择规则

1. 按加入顺序记录第一个游戏，不能依赖游戏列表原有排序。
2. 新增时过滤当前代理下已经入组的游戏。
3. 编辑时保留本组成员可选，过滤其他组成员。
4. 前端限制最多 10 个，后端执行同样的校验。
5. 允许保留只有一个游戏的组；空组不允许保存，清空成员应走删除组。

## 四、配置继承规则

创建时读取第一个游戏在该代理下的有效配置：优先使用代理专属配置，没有则使用游戏默认配置，并复制成组自己的配置快照。

复制后，组配置独立保存：

- 修改来源游戏配置，不自动修改组配置。
- 移除第一个游戏，不重新选择配置来源。
- 编辑成员，不重新复制配置，不改变 Base。
- 周期重置使用组保存的初始配置，不重新读取第一个游戏。

首版建议将成员编辑和组参数修改分开处理，防止修改 Base 时隐式改变余额，保证编辑成员时余额保持连续。

## 五、数据结构设计

将分组关系、水池运行数据、操作记录分开保存。

| 数据 | 主要内容 | 作用 |
| --- | --- | --- |
| 水池组配置 | 组 ID、代理 ID、组名称、来源游戏、配置快照、版本号、状态 | 保存组定义 |
| 水池组成员 | 代理 ID、游戏唯一标识、组 ID、加入顺序 | 定位游戏所属组 |
| 水池运行状态 | 代理 ID、池类型、池 ID、累计投注、赔付、税收、重置批次 | 保存实际计算数据 |
| 配置操作记录 | 操作编号、修改前后内容、执行状态、操作人、失败原因 | 支持追踪、重试与审计 |

数据库对“代理 ID＋游戏唯一标识”建立唯一约束。前端过滤之外，后端也检查重复归组、重复游戏和超过 10 个游戏的情况，防止两个管理员同时保存导致冲突。

实际计算统一按以下规则定位水池：

`代理＋游戏 → 查询所属组 → 有组使用组池，无组使用独立池`

游戏身份仍然保留，用于注单、报表和游戏自身控制；只有水池归属发生变化。

## 六、原游戏水池数据清除

清理需要同时覆盖 Redis 和开奖服务内存缓存。现有代码会定期把内存数据写回 Redis，只删 Redis 会导致旧数据再次写回来。

### 加入组时的处理顺序

1. 暂停受影响范围的新下注，等待正在执行的操作完成。
2. 确认旧池相关未结算订单、预占金额已经处理完。
3. 固定本次配置版本，创建新组池或读取现有组池。
4. 切换成员的水池归属。
5. 清理旧独立池的内存对象、待写回数据和 Redis 对应记录。
6. 确认新归属及清理结果后，恢复下注。

### 清理边界

- 清除原独立池用于余额计算的运行数据。
- 保留原游戏配置，供移出组后重新初始化。
- 保留历史注单、钱包流水和操作审计。
- 清理必须限定到当前代理、当前游戏对应的数据项。

现有部分累计数据同时承载水池计算和游戏统计，因此需要先拆清用途，不能直接删除整个代理统计集合。

## 七、未结算订单和并发处理

采用“等待旧订单处理完成，再切换”的方式。受影响游戏暂时停止接受新下注，已接受订单仍然允许结算、退款，完成后才清理旧池。

长局未结束时，后台显示“等待结算”，不能提前显示保存成功。

订单记录下注时的池归属和版本，后续派奖、退款及重试均按订单记录处理，避免只根据游戏当前所属组寻找水池。

所有改变水池的入口统一接入，包括：

- 普通下注。
- 多人游戏。
- 免费局或连续局。
- 赔付预占。
- 派奖。
- 退款。
- 失败回滚。
- 现有 Luck5 直接更新 Redis 的路径。

编辑成员时，“保留余额”指切换生效时不额外重置、搬移或拆分组余额；等待期间正常结算造成的余额变化仍然保留。

## 八、配置保存、同步和重置

后台保存配置与开奖服务实际生效分开记录，建议使用以下状态：

`待执行 → 等待结算 → 切换中 → 已生效／失败待重试`

### 保存与执行

1. MySQL 保存配置及操作任务。
2. 开奖服务依据操作编号和版本执行切换。
3. 开奖服务回报执行结果。
4. 重复收到同一个操作时，不得再次清池或重新初始化余额。
5. 失败任务保留明确状态，支持重试和追踪。

现有 Redis 消息通知可以继续使用，但需要增加持久化任务、执行确认和重试，不能仅凭“消息已发送”认定成功。

涉及多个开奖实例时，所有实例都必须遵守同一切换版本，防止旧实例继续写入原池。

### 周期与手动重置

- 周期重置沿用现有周期和排期规则。
- 组内成员共享一次重置结果。
- 新增游戏、移除游戏、编辑成员均不重新计算下次重置时间。
- 手动重置与周期重置使用同一套执行入口。
- 重置与配置切换互斥，避免重复初始化或覆盖余额。

## 九、接口和代码改动范围

### 建议新增接口能力

- 水池组列表。
- 水池组详情。
- 新建水池组。
- 编辑水池组。
- 删除水池组。
- 可选游戏列表。
- 操作状态查询。

新增、编辑接口携带请求编号；编辑额外携带版本号，防止覆盖其他管理员已经保存的修改。各接口沿用后台现有权限控制，并记录操作审计。

### 代码改动范围

| 模块 | 主要改动 |

## 十、验收重点

- 同代理同组游戏共用余额，不同代理互不影响。
- 新组只使用一次初始 Base，原游戏余额不转入新组。
- 增删成员后组余额连续，移出游戏从自己的 Base 重新累计。
- 第一个游戏被移除后，组配置和余额保持不变。
- 旧独立池的 Redis、内存和待写回数据全部清理，服务重启后也不会恢复旧余额。
- 超过 10 个游戏、重复归组、并发编辑均被后端正确拦截。
- 存在未结算订单时，派奖、退款不串池、不重复执行。
- 周期重置、手动重置、切换失败重试和服务重启恢复均正常。
- 游戏报表、历史注单及玩家钱包余额不受清池影响。
- 删除整个组后，所有原成员分别从自己的初始配置重新累计。

## 十一、实施和上线顺序

1. 完成表结构和统一水池定位。
2. 接通各结算入口与切换清理。
3. 完成管理接口和后台页面。
4. 进行联调、并发和异常恢复测试。
5. 先部署兼容代码，再开放配置入口。

未创建分组的代理继续按现有独立池逻辑运行。
