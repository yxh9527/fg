# 水池合并配置日志排查

更新日期：2026-10-28

## 一、查看位置

沿用项目现有 Zap 日志输出，不新增独立日志服务。目录以服务可执行文件所在位置为准；lottery 若指定了日志目录则以指定目录为准。

| 服务 | 位置 | 内容 |
| --- | --- | --- |
| web-api | logs/web-api.log | 管理接口、配置提交、定时重置触发和通知 |
| lottery | logs/debug/lottery.log | Debug、Info、Warn，包括任务执行、等待及清理阶段 |
| lottery | logs/error/lottery.log | Error，包括 SQL、Redis、租约和资金异常 |
| 管理页面 | 浏览器开发者工具 Console | 页面方法与水池接口请求日志，前缀 [pool-group] |

浏览器查看高频方法日志时需启用 Debug/Verbose 级别。当前服务端日志初始化会输出 Debug；高频方法使用 Debug 分级，关键操作使用 Info，正常等待使用 Warn，技术错误使用 Error。

## 二、统一字段

| 字段 | 含义 |
| --- | --- |
| module | 固定 pool-group，可先按此筛选 |
| function | 具体方法名，包含包名和接收者 |
| stage | 执行阶段，entry/exit 为方法开始和结束 |
| duration、elapsedMs | 方法耗时；elapsedMs 为毫秒 |
| agentId、groupId | 代理和水池组标识，有值时记录 |
| operationId、requestId | 数据库任务及管理请求标识 |
| batchId | 同一次重置的跨服务批次编号 |
| gameId、userId、roundId、currencyType | 开奖请求的游戏、玩家、局号和币种 |
| rpcMethod | 具体 gRPC 接口，便于区分下注、免费局、退款和结算 |
| error | 原始技术错误；调用者返回通用错误前也会记录真实失败步骤 |

不输出登录 token、租约 token、密码、完整配置、完整注单或原始请求体。浏览器错误日志也不会输出 Axios 请求配置。

## 三、重置执行链路

按相同 batchId 检索 web-api 和 lottery；再按 agentId、operationId 缩小范围。正常首次执行可看到：

1. reset_triggered：到期或手动触发。
2. batch_queued：数据库任务入库，尚不表示水池已清。
3. reset_published：已通知开奖服务。
4. batch_execute_begin：ResetPool 开始同步处理本批次。
5. gate_enabled：已限制受影响游戏的新下注。
6. status_applying：等待条件满足，开始执行。
7. reset_scan_done：已扫描该代理的现存统计及内存池。
8. redis_apply_begin、redis_applied：原子清理 Redis 并更新运行版本。
9. memory_invalidated：旧内存对象、映射和待写回标记已清理。
10. gate_cleared：解除切换门禁。
11. mysql_finalized：数据库任务确认 applied。
12. batch_execute_end：本轮批次处理结束，查看 unfinishedCount 是否为 0。

重复通知可能出现 already_applied、redis_replay_skipped 或 cache_current，表示已处理或本机缓存版本已同步，不应重复清除新投注。SQL 确认重试也可能跳过已经完成的 Redis 步骤。

方法的 exit 只表示该方法返回，不代表整个批次已完成。next_schedule_saved 只表示下一次排期保存成功，也不是本次清池完成标记。

## 四、核对 Redis 与内存是否清理

redis_applied 包含：

- clearMemberCount：计划处理的水池统计成员数。
- deletedRecordCount：Redis 实际删除的统计记录数，跨四类累计统计集合求和。
- nextRevision：应用后的运行版本。
- applied：1 表示本次应用；0 表示同一操作已经执行，跳过重复清理。

memory_invalidated 包含缓存对象数 cacheCount，以及 previousRevision、currentRevision。cache_current 表示已是当前版本，保留重置后产生的新投注。编辑成员时内存失效是为了重新加载，组余额仍以保留的 Redis 统计为准。

示意日志如下，编号仅为演示：

    {"module":"pool-group","function":"poolgroup.Store.Apply","stage":"redis_applied","agentId":7,"operationId":123,"deletedRecordCount":8,"nextRevision":2}

实际删除数为 0 可能是原来没有累计统计，或属于重复执行；不能仅凭一个数字认定故障，需结合 applied、运行版本、cache_current 及任务状态判断。

## 五、常见问题定位

| 最后出现的阶段或错误 | 检查方向 |
| --- | --- |
| batch_queued 后没有执行 | 是否有 worker_started；开奖服务是否运行；是否收到通知或被轮询读取 |
| waiting_earlier_tasks | 查看 earlierCount 和该代理前序任务的失败原因 |
| waiting_settlement | 查看 activeSessionCount、inflightCount、legacyRoundPending；旧局未结束时不强制清池 |
| lease_wait、超时 | 同一代理是否有长请求；检查租约连接和锁占用 |
| lease_renew_failed | 检查 Redis 连接及锁持有者变化；日志不会输出租约密钥 |
| redis_apply_begin 后失败 | 按 function、stage 和 error 检查具体 Redis 操作、统计类型或丢锁 |
| redis_applied 后没有内存同步 | 检查 syncPoolRuntimeMemory 的 panic/错误、cache_current 或实例退出 |
| memory_invalidated 后 SQL 失败 | 查看 Finalize 和事务错误；重试不能再次重置新池 |
| failure_status_write_failed | 任务执行失败后，数据库失败状态也未能写回，重点检查 MySQL |
| new_bet_blocked、continuation_required | 切换期间的正常限制，继续完成当前局 |
| funds_outcome_uncertain、uncertain_order_blocked | 资金结果待核实，保留现场，对照局号、钱包和流水；不能直接删标记或盲目重放 |
| method panic | 查看同条日志的 function、panicType 和 stack，原有异常传播行为保留 |

## 六、检索示例

在各自服务目录下，用批次或操作编号检索。以下操作编号仅为示例：

    rg -n 'pool-group' logs/web-api.log
    rg -n '"operationId":123' logs/debug/lottery.log logs/error/lottery.log
    rg -n 'waiting_settlement|lease_renew_failed|funds_outcome_uncertain' logs/debug/lottery.log logs/error/lottery.log

浏览器 Console 可筛选 pool-group；提交配置时复制 requestId，在后台服务中检索同一请求编号。

## 七、验证范围

自动化验证方法日志覆盖、入口与退出、Debug 关闭时错误仍可见、等待分级为 Warn、panic 原样传播、字段白名单、Redis 实际删除数，以及前端日志不泄露 token 且保留原错误。现有水池、重置、幂等及页面测试继续回归。真实部署环境的日志采集和跨实例联调仍需上线前验收。
