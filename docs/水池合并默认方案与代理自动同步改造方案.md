# 水池合并默认方案与代理自动同步改造方案

更新日期：2026-10-28

文档状态：需求已确认，已实现代码及自动化测试，待真实环境联调和上线验收。实现入口、接口和验证边界见[默认方案与自动同步开发说明](水池合并默认方案与自动同步开发说明.md)。

现有单代理功能基线见[水池合并配置功能实施方案](水池合并配置功能实施方案.md)，已实现范围及验证情况见[开发与验收说明](水池合并配置开发与验收.md)。默认范围、专属配置和自动同步以本文为后续改造依据。

## 一、已确认需求

1. 水池合并默认对全部代理应用，不再要求先指定某个代理。
2. 允许指定一个或多个代理单独处理。
3. 后续新增代理也自动应用默认合并方案。
4. 默认方案修改后，自动同步到仍然跟随默认的代理；使用专属配置的代理保留自己的设置。
5. 支持将使用专属配置的代理恢复为跟随默认方案。
6. 不同代理的水池运行数据和余额保持独立。

业务代码已按本方案开发；尚未部署或执行真实代理配置变更。

## 二、总体设计

采用“默认合并方案＋代理专属配置＋持久化同步任务”。

- 默认方案保存分组规则和适用范围，持续生效，覆盖范围内的现有代理及后续新增代理。
- 代理绑定记录该代理跟随默认还是使用专属配置，以及期望版本、实际生效版本和同步状态。
- 每个代理仍然拥有独立的实际水池组、配置快照和运行数据。
- 批次任务负责拆分、调度和汇总；现有单代理任务继续负责具体配置切换。

统一的是分组规则，不同代理不会因此共用同一份运行余额。默认方案不保存某个代理的当前余额，也不将该余额复制给其他代理。

### 适用范围与身份约定

以下为建议的实施口径，页面和接口都必须明确表达：

- “全部代理”指默认方案适用站点范围内、未删除的正式代理，不得由前端当前加载的一页代理列表代替。
- 适用范围明确支持全部站点或指定站点，页面显示实际范围和代理数量，不能把单个站点静默当作全站点。
- 每个站点最多命中一套有效默认方案；拒绝存在交叉覆盖的默认方案，首版不引入多层继承优先级。
- 测试代理 ID `0` 不包含在默认全量同步中，保留显式选择后的单独管理能力。不能使用 `agentId=0` 表示全部代理。
- 冻结、维护中的未删除正式代理仍纳入配置同步；同步成功不改变它们原有的业务启停状态。
- 权限由服务端校验。默认方案的持久化适用范围与操作人的当前页面筛选分开保存，后台自动同步不依赖其登录会话。
- 执行时发现代理已删除或移出方案范围，应停止新的下发并记录原因，不能计为已生效。

## 三、默认方案与专属配置规则

### 1. 默认方案

默认方案包含一组或多组水池合并定义，每组保存稳定的方案组标识、组名称、有序成员游戏和配置来源游戏。

- 同一方案内，一个游戏最多加入一个组；每组仍为 1–10 个游戏。
- 方案组标识在名称、顺序或成员编辑后保持不变，用于对应各代理的实际水池组。
- 默认方案每次修改产生不可变的新版本，历史版本保留，便于审计和追踪。
- 新代理初始化、周期补偿和手动重试都以该代理当前应该应用的最新版本为目标。
- 删除默认方案中的某个组，会对跟随默认的代理生成对应的删除组任务。
- 取消全部合并可以发布“空分组集合”版本；它不等于允许保存一个没有成员的组。历史方案及执行记录不能直接物理删除。

### 2. 代理专属配置

专属配置以“该代理完整的合并分组集合”为单位，不在首版引入逐个游戏、逐个字段的混合继承。

- 对指定代理单独编辑时，以其当前实际生效的完整配置作为初始草稿，再修改需要调整的组。
- 一次选中多个代理时，共同变更应用到各自草稿；各代理其余分组保留，冲突分别展示。
- 提交后，这些代理转为使用专属配置；后续默认方案更新不自动覆盖它们，也不会自动补入默认方案后来新增的组。
- 可以保存没有合并组的专属配置，表示该代理明确保持独立水池。
- 专属配置同样保存版本，并复用单代理校验、执行和审计流程。
- 多个代理应用同样的专属规则，也分别维护实际分组和余额。

### 3. 恢复默认

“恢复默认”表示将指定代理切换到当前最新默认方案，不是恢复到它过去曾经跟随的旧版本。

先预检查差异，再按实际组映射执行新增、编辑、删除。切换完成后才显示已生效；等待和失败状态不能提前显示为恢复成功。恢复任务与默认方案后续更新必须通过代理级调度协调，最终收敛到最新目标版本。

## 四、现有业务规则的延续

| 场景 | 处理方式 |
| --- | --- |
| 新建实际水池组 | 使用该代理下第一个选中游戏的有效配置，优先代理配置，再取游戏默认配置；从初始值重新累计 |
| 新增组成员 | 保留现有组余额；新成员的旧独立池余额不转入 |
| 移出组成员 | 保留原组余额；移出游戏从自己的初始配置重新独立累计 |
| 修改名称或成员顺序 | 保留实际组标识、已有组配置和余额 |
| 删除实际组 | 原成员分别恢复独立累计，组余额不分摊 |
| 分组规则没有变化 | 不产生清池或重新初始化操作 |
| 周期重置 | 沿用原有周期，保留分组规则和初始配置 |

默认方案同步不把一个代理的配置快照复制给其他代理。新建实际组时分别读取各代理自己的有效来源配置；已有实际组更新成员时继续保留其原配置快照。

成员切换仍遵循现有等待结算、原池绑定、缓存及 Redis 定向清理规则。保留历史注单、钱包流水和审计，不因同步整个删除代理统计数据。

## 五、任务与同步流程

### 1. 保存或更新默认方案

1. 校验适用范围、分组合法性和方案版本。
2. 预检查代理差异，展示预计新增、编辑、删除、不变、冲突、等待以及专属配置排除项。
3. 在事务中保存新方案版本和持久化同步批次；后台可分页生成代理明细，生成进度也要持久化。
4. 对跟随默认的代理建立同步任务，保存目标方案版本、代理配置版本及差异摘要。
5. 按稳定映射生成每个代理的整套分组变更任务，通过现有执行器等待相关订单结算后，原子切换该代理的完整归属。
6. 运行归属与数据库确认完成后，更新该代理的实际生效版本，再汇总批次进度。

预检查结果不是最终执行授权或锁。提交和实际执行仍需重新校验权限、代理归属及配置版本，避免预检查后其他修改造成覆盖。

任务逐步派发，每个代理同一时间只执行一个配置变更操作。一个代理等待或失败，不影响其他代理继续。实现新增 `layout` 任务：完整归属一次切换，避免游戏跨组移动出现重复归组；保留可复用组的 ID、初始配置和余额。Redis 原子切换与 SQL 最终确认仍分为两个阶段，不能解释为跨存储事务；重试依靠原操作编号恢复。

### 2. 新增代理自动初始化

1. 创建代理时，确定其所属站点及适用默认方案。
2. 在同一数据库事务中保存代理、初始绑定状态和初始化任务或待处理事件，防止代理已经创建但任务丢失。
3. 初始化执行前重新读取当前目标版本，避免创建过程中恰好发布了更新而遗漏新版本。
4. 为该代理建立实际水池组，并逐项等待执行确认。
5. 全部确认后记录实际生效版本，解除初始化限制。

初始化未完成时，默认方案涉及的相关游戏暂不开放新业务请求，其他不受影响游戏按原规则处理。限制必须在服务端落实，并能在任务失败、服务重启或缓存缺失时继续有效。

代理创建成功和水池初始化成功分别展示。初始化失败保留代理和任务，记录原因并重试，不通过反复创建代理恢复。尚无有效默认方案的站点沿用现有独立池规则；以后首次发布默认方案时，再纳入现有代理同步。

### 3. 指定代理单独处理

1. 搜索并多选代理，加载各自生效配置及版本。
2. 生成各代理的完整专属草稿，应用本次共同变更。
3. 预检查重复归组、来源配置缺失、未完成任务及版本冲突。
4. 对可执行项保存专属目标和持久化任务，明确列出未提交项及原因。
5. 各代理独立执行、汇总状态；等待或失败时展示生效旧配置与待应用新配置的区别。

专属目标一旦提交，后续默认更新不得再为其追加旧的默认同步任务。已经进入实际执行的任务必须先完成或明确恢复，再处理专属目标，不能直接删除执行中任务。

### 4. 定期补偿与重试

- 定期发现缺少绑定的新代理、期望版本与实际版本不一致的代理、遗漏明细及可重试失败任务。
- 扫描与代理创建事件配合，保证分页派发期间新增的代理也会被纳入。
- 重试复用稳定的请求编号和任务明细，只处理未完成步骤，已生效步骤不再初始化。
- 有多个未开始版本时可以合并为最新目标；已经开始执行的操作保留原始快照并先完成恢复，再应用最新差异。
- 同步、专属修改、恢复默认和周期重置复用代理级并发控制；执行前再次检查目标版本，避免旧任务覆盖新目标。
- 对缺失配置、数据冲突和需要人工核实的异常保留明确状态，不通过无限重试或伪造完成绕过。

## 六、数据结构建议

以下为新增逻辑实体建议，最终表名和字段在开发时按项目规范确定。

| 实体 | 主要内容 |
| --- | --- |
| 默认方案及版本 | 方案 ID、适用站点范围、版本、有序分组快照、发布人、发布时间 |
| 代理配置绑定 | 代理 ID、方案 ID、期望模式、已生效模式、期望版本、已生效版本、任务序号、同步状态、错误原因 |
| 代理专属配置版本 | 代理 ID、完整分组快照、版本、来源版本、操作人 |
| 分组映射 | 方案组或专属组的稳定标识、代理 ID、实际 groupId、当前实际组版本 |
| 同步批次 | 操作类型、目标版本、范围快照、请求编号、明细生成进度、各类状态数量、操作人 |
| 同步明细 | 批次 ID、代理 ID、目标版本、不可变差异计划、子操作关联、执行状态、错误和重试信息 |

现有 `pool_group`、`pool_group_member`、`pool_group_operation` 继续承担实际代理分组及执行记录。分组映射必须有唯一约束，不能依靠组名称识别同一组。

批次、代理明细和单组子操作分别建立幂等约束。实际生效版本必须在所有必要子操作确认之后更新；任务已入库、消息已发出或部分组已完成，都不能计为整个代理同步成功。

专属配置与默认配置之间切换时，保留可复用实际组的映射。成员集合等条件不足以唯一对应时应展示冲突，不为了方便而删除重建所有组。

## 七、后台页面与接口改造

### 页面

- 默认打开默认方案管理，不再以“先选择代理”为使用前提。
- 清晰展示方案站点范围、当前版本、跟随代理数量、专属代理数量和同步进度。
- 默认方案发布覆盖全部跟随代理；指定代理入口支持搜索、多选和单选，清晰提示将生成专属配置。
- 代理详情展示当前模式、实际生效版本、待应用版本、实际组余额及最近任务。
- 专属代理提供“恢复默认”操作，提交前展示差异和影响。
- 游戏选择需区分方案规则校验与各代理实际冲突；不能继续沿用一个代理的可选游戏列表作为全部代理的最终校验依据。
- 参数预览按代理展示，或提示不同代理来源配置可能不同，不能用单个代理的预览值代表全量代理。
- 批次明细按代理展示已生效、不变、待执行、等待结算、执行中、失败及排除原因，支持分页、筛选和只重试未完成项。
- 不展示混合代理的单一“当前组余额”；余额始终对应明确代理的实际组。

### 接口能力

- 默认方案及版本的查询、预检查、发布。
- 指定代理专属配置的预检查、提交和详情查询。
- 指定代理恢复默认的预检查和提交。
- 批次及代理明细查询、失败重试、代理同步状态查询。
- 新代理初始化事件消费与定期补偿入口。

新接口明确区分默认方案操作与指定代理操作，不能将原接口缺失 `agentId` 自动解释为全量执行。现有单代理入口需要接入专属模式和版本调度，避免绕过新机制直接修改后又被补偿任务覆盖。

## 八、已有代理配置接入

1. 建立默认方案草稿并展示现有代理配置差异，迁移本身不触发清池。
2. 规则一致且分组可以唯一对应的代理，建立稳定映射并关联为跟随默认；保留原有配置快照、实际组 ID 和余额。
3. 有差异的代理列出清单，由操作人决定同步默认还是保留为专属配置。
4. 对未完成选择、映射不明确或存在旧任务的代理，保留迁移待处理状态，阻止自动覆盖。
5. 确认范围后创建持久化任务，先用少量代理验证，再扩大范围。

配置快照数值因代理不同而不同，不应仅因此判定为规则冲突；是否能直接接入需结合有序成员、来源规则和已有映射检查。

建议实施顺序：

1. 明确范围约定，完成表结构、版本模型及稳定映射。
2. 完成默认方案、专属模式和差异预检查。
3. 接入持久化批次及现有单代理执行流程。
4. 接入新代理初始化、服务端限制与定期补偿。
5. 完成管理页面、历史配置迁移预览与相关测试。
6. 测试环境验证故障恢复和并发后，按小范围到全量顺序上线。

## 十、验收清单

- [ ] 不选择具体代理也能维护默认方案，范围和影响数量明确。
- [ ] 默认方案能应用到范围内全部跟随代理，各代理余额独立。
- [ ] 站点范围不会被页面历史筛选值静默改变；不支持的范围重叠被拒绝。
- [ ] 可指定一个或多个代理生成专属配置，未选代理不受影响。
- [ ] 专属代理不被后续默认更新覆盖，空专属配置也保持有效。
- [ ] 恢复默认最终应用最新版本，过程状态和失败原因可见。
- [ ] 新增代理在无额外人工操作时自动完成初始化。
- [ ] 初始化未完成或失败时，相关游戏的服务端限制有效，重启后仍有效。
- [ ] 新代理创建与方案更新并发、批次分页派发期间新增代理，最终都收敛到最新目标。
- [ ] 来源游戏配置按代理分别读取，缺失或冲突时准确报告对应代理。
- [ ] 名称或成员编辑保留可复用实际组与余额，不变配置不产生重复清池。
- [ ] 跨组移动、多组部分完成和版本冲突具有明确状态及恢复方式。
- [ ] 某代理等待结算或失败，不阻塞其他代理；批次不会提前显示全部成功。
- [ ] 重复提交、重复事件、失败重试和服务重启不会重复初始化已完成组。
- [ ] 默认更新、专属修改、恢复默认和重置并发时，旧任务不会覆盖新目标。
- [ ] 定期补偿能恢复遗漏任务，无法自动解决的异常保留人工处理信息。
